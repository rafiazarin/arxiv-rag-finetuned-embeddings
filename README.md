# Does Fine-Tuning Embedding Models Help RAG Retrieval? A Controlled PubMed Evaluation

An evaluation of whether fine-tuning an embedding model on LLM-generated query–passage pairs improves
retrieval for RAG, and of whether a common automatic way of judging retrieval can be trusted.
Built with free tools (local Mac + free Colab T4).

**Model:** [`rafiazarin/bge-base-pubmed-finetuned`](https://huggingface.co/rafiazarin/bge-base-pubmed-finetuned)
· **Interactive demo:** [PubMed side-by-side search](https://huggingface.co/spaces/rafiazarin/pubmed-search-demo)
(retrieval only, 8-bit models in the browser; not the evaluation used for the results below)

## Key findings (PubMed, 90 human-written questions)

1. **Fine-tuning on 1,300 synthetic pairs showed no statistically reliable improvement on the objective metric.**
   Pre-registered tests: p = 0.299 on 2,000 abstracts, and p = 0.1158 on 20,000 abstracts, where the fine-tuned
   model scored lower (MRR 0.7611 vs. 0.8019). Paired 95% CIs for the MRR difference (fine-tuned minus untuned):
   −0.0148 to +0.0537 at 2,000 abstracts, −0.0907 to +0.0056 at 20,000. This held in a setup that favors
   fine-tuning (see [Scope](#scope)).
2. **Only an automatic cross-encoder judge showed a fine-tuning gain** (+0.0445 MRR, 3 seeds, p = 0.0229), and
   that judge agreed poorly with human labels (Cohen's kappa 0.2 on 60 items), so its results should not be
   trusted on their own.
3. **The base model choice had the clearest effect in this setup.** Untuned BGE-base beat nomic-embed-text on MRR
   in every setting tested (p = 0.0011 on 2,000 abstracts, p < 0.0001 on 20,000, p = 0.0323 under the automatic
   judge). Hit@3 was significant only on the 20,000-abstract corpus (p = 0.0033). Neither model used its
   recommended query prefix, so this comparison is provisional.

## Setup

- **Collection.** The first 2,000 abstracts of `ccdv/pubmed-summarization` (train split) that pass a length
  filter, shuffled with seed 42, split into 7,627 chunks (400 characters, 50-character overlap). A harder
  version uses the first 20,000 abstracts (75,862 chunks, a superset of the 2,000). FAISS exact cosine search.
- **Models.** `BAAI/bge-base-en-v1.5` (untuned), the same model fine-tuned, and `nomic-embed-text` (via Ollama)
  as a second baseline.
- **Fine-tuning.** 1,300 query–abstract pairs generated by gemma3:4b from the 2,000-abstract collection.
  MultipleNegativesRankingLoss, 5 epochs, batch 32, lr 2e-5, 100 warmup steps; final model saved.
- **Evaluation questions.** 90 questions written by hand, each from one abstract in the collection.
- **Relevance rules.**
  - *Metric 1 (objective):* a retrieved chunk is relevant if it comes from the question's source abstract.
  - *Metric 2 (automatic judge):* a retrieved chunk is relevant if `cross-encoder/ms-marco-MiniLM-L-6-v2`
    scores it ≥ 0 against the source abstract.
- **Statistics.** Hit@3, MRR@3, NDCG@10 with bootstrap 95% CIs; McNemar (Hit@3) and paired sign-flip
  permutation (MRR) tests; paired bootstrap CIs for MRR differences. Primary tests were fixed before running.

### Scope

This study tests **adapting a retriever to a fixed collection**: the training questions were generated from the
same collection that is later searched, a standard setup for customizing retrieval to a known document set.
The 90 evaluation questions are separate and human-written; for 63 of them, the source abstract also had a
generated training question. **Generalization to unseen documents is not tested.** An exploratory split by
seen/unseen abstracts is in [`experiments/paired_ci_and_overlap.json`](experiments/paired_ci_and_overlap.json).

### Checking the automatic judge against human labels

From 324 unique question–chunk pairs (top-3 results of both BGE models), 30 the judge called relevant and 30 it
called not relevant were sampled (seed 42), shuffled, and labeled by the author without seeing the judge's
decision. Question: does the chunk contain the information that answers the question?
Script: [`step13_matcher_validation.py`](step13_matcher_validation.py);
results: [`experiments/matcher_validation.json`](experiments/matcher_validation.json).

| | Human: yes | Human: no |
|---|---|---|
| Judge: relevant | 14 | 16 |
| Judge: not relevant | 8 | 22 |

Precision 0.4667, negative predictive value 0.7333, Cohen's kappa 0.2, agreement re-weighted to the pool 0.6379.
Disagreement was concentrated in chunks from the source abstract (agreement 19/42) rather than chunks from other
abstracts (17/18): the judge mostly detects "same abstract", not "answers the question".

## Limitations

1. Neither relevance metric equals "answers the question": the automatic judge agreed poorly with human labels,
   and the objective metric counts any chunk of the source abstract.
2. Human labels come from one annotator (the author), who could see the source abstract, on 60 items.
3. 90 evaluation questions; they were written from the abstracts, which makes the source abstract easy to
   retrieve (ceiling effect at 2,000 abstracts; the 20,000-abstract check addresses this).
4. Generalization to unseen documents is not tested (see [Scope](#scope)).
5. Training questions are LLM-generated; no hyperparameter search.
6. Queries were encoded without BGE's query instruction prefix, and nomic without its task prefixes.
7. Chunks are fixed 400-character slices, which can split sentences.
8. The nomic score changed between the original run and the re-run on identical data, most likely because of a
   newer Ollama version. Only numbers from the same run are compared.

## Reproduce

```bash
git clone https://github.com/rafiazarin/finetuned-embeddings-rag-eval
cd finetuned-embeddings-rag-eval
python3.12 -m venv .venv && source .venv/bin/activate
pip install torch==2.12.0 sentence-transformers==5.5.1 transformers==5.9.0 faiss-cpu==1.13.2 \
            numpy==2.4.6 scipy==1.17.1 datasets==4.8.5 ollama==0.6.2 tqdm==4.67.3
ollama pull nomic-embed-text                        # with `ollama serve` running

python restore_pubmed_pool.py                       # rebuilds data/pubmed_pool.json, verified
python step10b_build_pubmed_index.py                # nomic baseline index
python step11_eval_pubmed_baselines.py --from-hub   # Metric 2, uses the published model
python step13_matcher_validation.py score           # judge vs. human labels (labels in data/)
python step18_paired_ci.py                          # paired CIs and overlap, from saved results
# Metric 1 (step14_source_match_eval.py, step15_scale_pubmed.py) and the epoch-1 comparison need local models:
# run notebooks/step10d_train_pubmed_bge.ipynb in Colab and unzip into experiments/.
# Seed study: notebooks/step12_pubmed_seed_study.ipynb (Colab).
```

`requirements.txt` lists the full original environment; the command above installs only what is needed here.

## Project history

This project began in May–Jun 2026 as an arXiv study that reported large fine-tuning gains. An audit in
Sep 2026 found a missing untuned baseline, a checkpoint-selection bug, and misreported settings; the arXiv
models and training data were then lost in a hardware failure, so that study cannot be re-run. The PubMed study
above was rebuilt and re-run from scratch. The original arXiv results and an early observation about evaluation
contamination are kept, with caveats, in [`docs/original-arxiv-study.md`](docs/original-arxiv-study.md).
