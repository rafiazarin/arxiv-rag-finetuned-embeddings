# Domain-Adaptive RAG with Fine-Tuned Embeddings

A retrieval-augmented generation pipeline where the embedding model is 
fine-tuned on domain-specific query-passage pairs, evaluated against 
BM25 and off-the-shelf embeddings on held-out queries.

Built entirely with free, local tools — no paid APIs, no cloud compute 
beyond a free Colab T4 GPU session for training.

---

## Results

Evaluated on 100 held-out queries never seen during training.  
Metrics: Hit Rate@3 and MRR@3 (pure retrieval, no LLM judge).

| Method | Hit Rate@3 | MRR@3 |
|---|---|---|
| BM25 Okapi (keyword baseline) | 0.70 | 0.6517 |
| nomic-embed-text (off-the-shelf dense) | 0.69 | 0.6117 |
| **all-MiniLM-L6-v2 fine-tuned (ours)** | **0.71** | **0.6633** |

Fine-tuning improved MRR by **+8.4%** over the off-the-shelf embedding 
baseline on in-distribution arXiv CS queries.

### Out-of-distribution evaluation

Testing on 10 general CS queries outside the training distribution 
revealed retrieval degradation in the fine-tuned model:

| Model | Mean Keyword Relevance (OOD) |
|---|---|
| nomic-embed-text (baseline) | 0.1122 |
| Fine-tuned (ours) | 0.0633 |

This is consistent with **catastrophic forgetting** — a known phenomenon 
where fine-tuning on a narrow domain degrades performance on out-of-domain 
queries. See [Limitations](#limitations) for analysis and proposed fixes.

## Architecture
arXiv CS abstracts (5,000 docs, 2021)
↓
Chunking (400 chars, 50 overlap)
↓
13,050 text chunks
↓
FAISS IndexFlatIP (cosine similarity)
↓
Top-3 chunk retrieval
↓
Ollama gemma3:4b → Answer

Fine-tuning path:

3,000 synthetic (query, passage) pairs
generated by gemma3:4b on M2 MacBook
↓
MultipleNegativesRankingLoss
all-MiniLM-L6-v2 base model
5 epochs, batch size 32
Free Colab T4 GPU (~25 min)
↓
Fine-tuned model (384-dim, 80MB)
hosted on HuggingFace Hub

## Key Technical Decisions

**Why MultipleNegativesRankingLoss?**  
For each (query, passage) pair in a batch, all other passages become 
implicit negatives. This avoids the need for manually labeled hard 
negatives while still producing a strong retrieval signal. Efficient 
and well-suited for synthetic training data.

**Why FAISS IndexFlatIP over HNSW or IVF?**  
With 13,050 vectors the corpus is small enough that exact search 
(IndexFlatIP) is fast and eliminates approximation error. HNSW would 
be appropriate at 1M+ vectors.

**Why Hit Rate and MRR instead of RAGAS?**  
RAGAS uses an LLM as a judge for faithfulness and relevancy metrics. 
During development, RAGAS produced NaN scores when using local Ollama 
models due to output parsing failures — a known compatibility issue 
with non-OpenAI LLMs. Since this project fine-tunes the *embedding* 
model (not the generator), retrieval-focused metrics directly measure 
what changed. Hit Rate and MRR are standard information retrieval 
metrics that require no external judge.

**Why synthetic training pairs?**  
No human-annotated query-passage pairs exist for this specific arXiv 
subset. Using an LLM to generate questions for each passage is a 
standard approach (see: GPL, InPars) that scales to any corpus without 
annotation cost.

## Notebook Demo

`notebooks/demo.ipynb` runs the full pipeline interactively, comparing 
all three retrieval methods on three queries:

**Query 1 (in-distribution):** "What is the convergence rate of gradient 
descent for convex functions?"  
→ Fine-tuned model retrieves a convex optimization semidefinite 
programming paper, closer to the query intent than baseline.

**Query 2 (in-distribution):** "How are hidden Markov models applied to 
sequence labeling problems?"  
→ BM25 wins on exact terminology (Viterbi algorithm). Both embedding 
models retrieve a protein HMM paper — topically adjacent but not 
directly on-topic. Shows a known weakness of dense retrieval on 
exact-match queries.

**Query 3 (OOD):** "How do transformer attention mechanisms work?"  
→ All three methods fail. The 2021 arXiv corpus is sparse on transformer 
architecture papers; BM25 retrieves a linguistics paper, embedding 
models retrieve a neuroscience attractor network paper. Demonstrates 
corpus coverage limitations.

## Limitations

**1. Synthetic evaluation set**  
Training pairs and evaluation pairs were generated by the same LLM 
using the same prompt template. This means the eval distribution 
partially reflects the generator's patterns rather than real user 
queries. A stronger evaluation would use human-written questions or 
queries from a separate source.

**2. Catastrophic forgetting**  
Fine-tuning on 2,700 physics/math arXiv pairs caused retrieval 
degradation on general CS queries (OOD delta: -0.049). The model 
specialised at the cost of general semantic understanding.

Production mitigations:
- Mix domain-specific pairs with general MS MARCO pairs during training
- Use a larger base model (bge-base-en-v1.5) with more capacity
- Apply Elastic Weight Consolidation (EWC) regularization
- Monitor OOD eval score as an early stopping signal alongside in-domain loss

**3. Corpus size**  
5,000 abstracts is a small corpus. Several evaluation queries had no 
relevant documents in the corpus at all (both models scored 0.0), which 
inflates apparent failure rates beyond what the embedding models 
themselves are responsible for.

model = SentenceTransformer("rafiazarin/arxiv-cs-embedding-finetuned")
